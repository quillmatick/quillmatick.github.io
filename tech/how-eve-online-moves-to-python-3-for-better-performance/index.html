How EVE Online Moves to Python 3 for Better Performance

See how EVE Online moves to Python 3 to optimize server performance. Learn the technical migration steps to reduce lag and boost stability. Read the full guide.

QM
Quillmatick Staff August 31, 2026
8 min read

Migration Strategy Overview

  • Phase-by-phase refactor: Keep services on Python 2.7 while feature-flagging Python 3 code on test clusters (e.g., Singularity). Consequently, regressions appear early, before live deployment on Tranquility.
  • Compatibility tools: Run python-future and 2to3 to rewrite legacy syntax such as print statements and long integer literals. Therefore, a single codebase runs on both runtimes.
  • Eliminate Python 2-only constructs: Replace the old garbage collector and manual Unicode handling with Python 3’s unified str type and improved memory manager. As a result, latency drops in high-concurrency tasks.
  • Adopt native async/await: Refactor I/O-heavy pathways—fleet-fight calculations, market queries—to Python 3’s built-in asynchronous primitives. Thus, overhead from external async libraries disappears.
  • Maintain C++ bindings: Update Boost.Python bindings to target Python 3, keeping performance-critical C++ services interoperable without costly rewrites.

Introduction

EVE Online operated on a single Python version for over two decades. On 25 August 2026, the EVE Evolved migration switched to Python 3. Moreover, the move accelerates bug resolution, enables new features, and delivers smoother gameplay for capsuleers. Furthermore, Python 3 offers speed gains, superior memory handling, and a modern library ecosystem unavailable to Python 2.7.

Understanding the Legacy Python Architecture

Historical Context

  • 2003: Stackless Python powers the initial server stack, using lightweight “tasklets” for massive concurrency.
  • 2007: Upgrade to Python 2.5.
  • 2010: Move to Python 2.7, which persisted for sixteen years.

Core Limitations of Python 2

  • Global Interpreter Lock (GIL) throttles parallel execution, creating bottlenecks in high-concurrency environments.
  • Manual Unicode encoding/decoding increases code complexity and error risk.
  • Legacy garbage collector raises latency under load.

How the Python 3 Migration Works

Dual-Runtime Deployment

  1. Deploy feature flags on Singularity test clusters.
  2. Run Python 2.7 and Python 3 side by side.
  3. Gradually enable Python 3 pathways while monitoring performance metrics.

Automated Code Conversion

  • Execute 2to3 across the repository to replace deprecated syntax.
  • Apply python-future for forward-compatible imports, enabling a single source tree.

Refactoring for Async I/O

  • Identify I/O-bound functions (e.g., market data fetch, combat simulation).
  • Replace custom async frameworks with async def and await.
  • Benchmark using the asyncio event loop to verify reduced latency.

Updating C++ Bindings

  • Modify Boost.Python modules to compile against Python 3 headers.
  • Run integration tests to confirm core engine services maintain performance.

Key Benefits & Real-World Applications

  • Performance boost: Benchmarks show up to X% improvement in p99 latency versus legacy setups.
  • Reduced maintenance: A unified codebase eliminates separate Python 2 patches.
  • Enhanced scalability: Native async support lets the server handle more concurrent pilots without additional hardware.
  • Future-proofing: Access to modern libraries such as uvloop and orjson accelerates feature development.

Challenges, Risks & Mitigation

  • Compatibility testing: Ensure every service runs correctly under both runtimes. Mitigation: extensive automated test suites.

  • C++ binding stability: Updating Boost.Python may introduce subtle bugs. Mitigation: run regression benchmarks after each build.

  • Performance regression: Async refactor could increase latency if misused. Mitigation: monitor p99 latency and roll back feature flags quickly.

  • Compatibility gaps: Some third-party modules lack Python 3 wheels. Therefore, the team isolates these modules behind adapters until replacements appear.

  • Performance regressions: Async refactors may introduce subtle latency spikes. Consequently, continuous profiling and automated regression tests guard against degradation.

  • C++ binding breakage: Updating Boost.Python can cause ABI mismatches. Thus, the migration team maintains a parallel test suite that validates binary compatibility on each commit.

Conclusion

EVE Online’s shift to Python 3 transforms its server architecture from a legacy bottleneck into a high-performance platform. By combining phased refactoring, automated conversion tools, native async, and updated C++ bindings, CCP ensures a seamless transition for capsuleers while positioning the game for future innovations. Consequently, the migration not only resolves existing performance issues but also unlocks new development opportunities for the MMO’s evolving universe.

  • Memory management – The garbage collector lacks the precision of Python 3.
  • Unicode handling – Splitting text between str and unicode makes localization a nightmare.
  • No native async/await – Without built-in asynchronous I/O, developers rely on custom wrappers. This adds latency to fleet-fight calculations and market-hub queries.

These constraints eventually lowered the performance ceiling of EVE’s server farms.

Why a Migration Was Inevitable

Internal audits proved that Python 2 was holding EVE back. Community pressure mounted as essential libraries vanished from the retired ecosystem. Performance stagnation, maintenance overhead, and security risks left CCP with no choice.

The transition requires more than just a compiler update; it demands a total rethink of how the game handles data at scale.

How the Python 3 Migration Works: A Deep Dive

Project Planning and Incremental Refactoring

CCP chose a phased approach. Stage 1 makes the code Python 3-ready while it still runs on Python 2.7. Feature flags allow the team to toggle new code paths on Singularity (the test server), isolating regressions before they hit the Tranquility live cluster.

Compatibility Layers and Tooling (2to3, Futurize)

The team uses Python-Future, a library based on the 2to3 rewrite engine. This utility applies “fixers” to transform obsolete syntax into a hybrid form compatible with both Python 2.7 and Python 3. It strips the L suffix from long integers and converts old-style print statements.

Integration with Existing C++ Core Services

EVE’s performance-critical core remains in C++. Boost.Python handles the bridge between the two languages. Since the Carbon engine already runs on Python 3 for the EVE Frontier project, the bindings are already validated. CCP isn't replacing the C++ layer; they are updating the Python "steering wheel" that controls it.

Updating the language is one thing, but the real payoff appears in the server metrics.

Key Benefits & Real-World Applications

Performance Gains in CPU-Bound Simulations

CCP hasn't released raw benchmarks, but they noted that recent Python 3 releases offer the largest speedups in the language's history. Expect combat calculations and market simulations to snap faster once the interpreter switch completes.

Improved Memory Efficiency and Garbage Collection

Python 3’s refined garbage collector slashes server RAM usage. For a game that stays online 23.75 hours a day for millions of players, this reduces operational costs and stabilizes shard performance.

Enhanced Developer Productivity and Ecosystem Access

Type hints, async/await, and a unified string type make the code cleaner. Modern debugging tools—exclusive to Python 3—allow the team to kill bugs faster. For the player, this means faster feature rollouts.

Even with these gains, moving 2.4 million lines of code is a minefield.

Challenges, Risks & How to Overcome Them

Legacy Code Compatibility Issues

The codebase contains 2.4 million lines of Python. Some of this code is older than Python 2.7. An initial scan showed 95.9% of the 20,000 files compiled under both interpreters. The remaining 3,300 lines required manual surgery. The culprits?

  • ~1,500 old-style print statements
  • ~800 “long” literals (123L)
  • ~600 deprecated exception clauses
  • 50 uses of the obsolete <> operator

Syntax is the easy part. The real danger lies in the 20,000 lines that compile but behave differently—specifically division semantics (1 / 2 yielding 0 in Python 2 vs 0.5 in Python 3). One wrong calculation could break a ship's fitting or a market trade.

Downtime Minimization Strategies

CCP uses blue-green deployments and canary testing. By toggling new code paths on a subset of servers, they isolate failures without crashing the entire player base.

Security and Regression Testing

The team expanded the test suite to cover both interpreters. Automated regression tests run on every commit, while fuzz testing probes for edge cases. Third-party audits will verify that the transition doesn't open new security holes.

Expert Insights & Industry Trends

Interviews with CCP Engineering Leads

The EVE Online Team views this as “infrastructure for the next twenty years.” The success of the Carbon engine in EVE Frontier proved the stack could handle the main game's scope.

Comparison with Other MMOs Adopting Python 3

EVE Echoes and Star Citizen have faced similar migrations. The industry-wide challenge is the same: modernize a massive legacy codebase without interrupting a live service. CCP’s incremental, test-driven strategy is now the blueprint.

For other studios facing this nightmare, the process boils down to a few strict rules.

Practical Tips & Best Practices for Large-Scale Python Migrations

Establish Robust Automated Testing Pipelines

Frequently Asked Questions (FAQ)

1. Why can’t EVE Online stay on Python 2? Python 2 died in 2020. No more security patches. No more modern libraries. Staying would mean building custom tools for a dead language.

2. How does Python 3 improve in-game latency? A more efficient bytecode interpreter and native async/await reduce the time spent on CPU-bound tasks and I/O. This means smoother fleet fights.

3. Will the migration affect existing player data? No. Serialization formats for assets and ISK balances remain untouched. Only the runtime changes.

4. What are the biggest technical hurdles CCP faced? Converting legacy syntax and fixing "silent" behavioral changes, like division semantics, across 2.4 million lines of code.

5. How does the move impact future content updates? Modern tooling lets developers prototype faster. Type hints and unified strings reduce bugs, speeding up the delivery pipeline.

6. Can other game studios replicate EVE’s migration strategy? Yes. Audit compatibility $\rightarrow$ automate syntax $\rightarrow$ manually review semantics $\rightarrow$ deploy via canaries $\rightarrow$ monitor with observability stacks.

Conclusion

The shift from Python 2.7 to Python 3 is a pivotal moment for EVE Online. By dismantling a 2.4 million-line legacy monolith through automation and rigorous testing, CCP secures better performance and faster development. Players won't see the code change, but they will feel it in the responsiveness of the universe for the next two decades.
