Google Has Stopped Pushing Git Tags for Android Source Code

Google stopped pushing git tags for Android source code. Learn why this change happens and how to manage your builds efficiently to save time. Read more here.

QM
Quillmatick Staff August 23, 2026

Overview of the Tagging Change

What Google Changed

  • Google announced that the Android Open Source Project (AOSP) will no longer publish Git tags for new releases.
  • The decision removes the traditional git describe --tags shortcut that many CI pipelines rely on.
  • Consequently, every downstream build must obtain version information from an alternative source.

Immediate Technical Consequences

  • Automation scripts that parse tags will return empty results, causing build failures.
  • Version-tracking tools lose their reference point, which hampers reproducibility.
  • Security audits that depend on tag-based provenance lose a critical audit-trail element.

Compliance Implications

  • Regulations such as GDPR, CCPA, and ISO 27001 require an immutable chain of custody for source code.
  • Without tags, organizations risk non-compliance during external assessments.
  • Therefore, enterprises must implement compensating controls to satisfy audit requirements.

Deterministic Build Strategies

Replace Tag-Based Versioning

  • Capture the exact commit SHA at build time instead of relying on a tag.
  • Store the SHA in a plain-text VERSION file located at the repository root.
  • Embed the file’s content into binary metadata using build-time flags.

Embedding Commit SHA in Binaries

  • Use compiler options such as -DVERSION=$(git rev-parse HEAD) for Java or -X main.version=$(git rev-parse HEAD) for Go.
  • Consequently, each binary self-identifies its source commit, enabling traceability without tags.

Sample Build Script

#!/usr/bin/env bash
# Deterministic build script – captures commit SHA and writes VERSION file

set -euo pipefail

# Obtain the full commit hash
COMMIT_SHA=$(git rev-parse HEAD)

# Write SHA to VERSION file
echo "$COMMIT_SHA" > VERSION

# Build Android component with version flag
./gradlew assembleRelease -PversionCode=$COMMIT_SHA
  • Explanation: The script runs in a clean checkout, guarantees that the same SHA produces identical binaries, and eliminates tag dependency.

Automated Provenance Metadata

CI Pipeline Enhancements

  • Extend the CI workflow to collect commit hash, author email, GPG signature, and build timestamp.
  • Generate a signed JSON manifest that aggregates these fields.

Signed JSON Manifest Structure

Field Description
commit_sha Full 40-character Git hash of the source.
author_email Email address of the commit author.
gpg_signature ASCII-armored signature of the commit.
build_time ISO-8601 timestamp of the build execution.
artifact_hash SHA-256 digest of the produced binary.
  • Implementation tip: Use gpg --clearsign to sign the manifest, then store the signature alongside the manifest.

Storing Manifests in Immutable Registries

  • Push the signed manifest to an OCI registry or a dedicated artifact store that enforces immutability.
  • Consequently, auditors can retrieve a tamper-evident record for any released binary.

Internal Tagging Service Architecture

Git-Hook Service Design

  • Deploy a lightweight service that listens to post-receive hooks on the internal mirror of AOSP.
  • The service automatically creates lightweight tags (e.g., enterprise-13.0.0_r1) after each successful upstream sync.

Tag Naming Conventions

  • Adopt a deterministic naming scheme:
<product>-<major>.<minor>.<patch>_r<revision>
  • For example, android-13.2.0_r3 conveys product, version, and internal revision.

Integrity Verification Workflow

  • Schedule a nightly job that cross-checks newly created tags against official AOSP release notes.

  • If a mismatch occurs, the job raises an alert and rolls back the tag creation.

  • Result: The internal tagging service restores the missing link between source and binary, while preserving compliance.

SBOM Integration with Commit Data

Tool Configuration (Syft & CycloneDX)

  • Configure Syft or CycloneDX to read the commit SHA from the build manifest rather than a Git tag.
  • Example Syft command:
syft packages --source git@github.com:myorg/android.git@$(cat VERSION) -o cyclonedx-json > sbom.json

Aligning SBOM with Build Manifest

  • Include the commit_sha field inside the SBOM’s metadata.component section.
  • Consequently, vulnerability scanners can map each component directly to the source commit.

Compliance Reporting Benefits

  • Auditors receive a single source of truth that links SBOM, binary hash, and commit SHA.
  • This alignment satisfies ISO 27001 Annex A.12.1.2 requirements for traceable artifact provenance.

Rapid Rollback & Hot-Patch Process

Golden-Commit Registry

  • Maintain a database that maps each released binary’s version identifier to its golden commit SHA.
  • The registry should expose a simple API:
GET /registry/v1/golden?binary=android-13.2.0_r3

Rebuilding from SHA

git checkout <SHA>
./gradlew assembleRelease
  • By checking out the exact SHA, teams can reproduce the original binary without waiting for an upstream tag.

SLA-Driven Patch Deployment

  • Define a hot-patch SLA (e.g., 48 hours from vulnerability disclosure).
  • When a critical CVE appears, the workflow triggers:
  1. Query the golden-commit registry for the affected binary.
  2. Checkout the SHA and apply the security fix.
  3. Re-sign the artifact and publish to the OTA server.
  • Consequently, enterprises meet security response commitments even in a tag-less environment.

Monitoring Upstream Branch Health

Alerting Mechanism

  • Implement a cron job that polls the AOSP refs/heads/master branch for new commits.
  • If a new commit appears without a corresponding internal tag, the job sends a Slack or email alert.

Automated Tag Creation Trigger

  • The alert invokes the internal tagging service via its REST endpoint, ensuring immediate tag generation.
curl -X POST https://tagging.service.internal/create \
 -d '{"branch":"master","sha":"'"$NEW_SHA"'"}'

Implementation Best Practices & Security Guardrails

Secure CI Configuration

  • Store GPG private keys in a vault (e.g., HashiCorp Vault) and inject them at runtime.
  • Use short-lived CI tokens to limit exposure.

Immutable Artifact Storage

  • Enforce write-once policies on the OCI registry to prevent retroactive changes.
  • Enable content-addressable storage so that artifact hashes serve as unique identifiers.

Regular Audits

  • Schedule quarterly reviews of the golden-commit registry against production binaries.
  • Conduct automated diff checks between stored SBOMs and the latest vulnerability database.

Incident Response Playbook

  • Define clear escalation paths for missing tags, failed manifest signatures, or SBOM mismatches.
  • Practice tabletop exercises quarterly to ensure the team can rebuild and patch within SLA.

Frequently Asked Questions

1. Why does Google no longer push Git tags for AOSP? Google stopped publishing tags to simplify its release workflow and to reduce maintenance overhead. However, the change unintentionally disrupts downstream automation that depends on tag-based versioning.

2. Can I continue using git describe --tags after the change? No. Without upstream tags, git describe returns an error or an ambiguous description. Therefore, you must switch to commit-SHA-based identification or implement an internal tagging service.

3. How does a deterministic build improve reproducibility? A deterministic build captures the exact commit SHA and embeds it into the binary. Consequently, any rebuild using the same SHA produces an identical artifact, eliminating variability caused by missing tags.

4. What is the role of a signed JSON manifest in compliance? The manifest records provenance data (SHA, author, timestamp) and is cryptographically signed. Auditors can verify the signature to confirm that the metadata has not been altered, satisfying ISO 27001 and other regulatory requirements.

5. Is an internal tagging service safe from tampering? When the service creates lightweight tags on a protected internal mirror and stores them in an immutable registry, the tags become tamper-evident. Additionally, signing each tag with a GPG key adds a cryptographic guarantee of authenticity.

6. How quickly can I generate a hot-patch after a vulnerability is disclosed? By leveraging the golden-commit registry, you can locate the exact source SHA, apply the fix, rebuild, and redeploy within the defined SLA (often 24-48 hours). This process bypasses the need for an upstream tag and reduces mean time to remediation.

Key Capabilities & Evaluation Criteria to Consider

If the upstream source is no longer providing the markers, you must build your own. But how do you ensure your internal markers hold up under a regulatory audit?

Must-Have Features for Enterprise Deployments

  • Deterministic build reproducibility – Lock builds to a specific commit SHA. This guarantees that the binary you ship today can be rebuilt tomorrow without divergence.
  • Automated provenance tracking – Metadata must include commit hash, creator identity, and signing certificates to satisfy ISO 27001 Annex A.12.1.2 (Change Management).
  • Rollback & hot-patch mechanisms – Revert to a known-good commit or apply a one-off patch instantly. Zero-day exploits don't wait for upstream releases.

Integration & Compatibility Requirements

  • CI/CD compatibility – Native plugins for Jenkins, GitLab CI, and Azure DevOps ensure seamless adoption.
  • Android Gradle Plugin (AGP) 8.x support – The tool must expose properties Gradle can read, such as android.defaultConfig.versionName.
  • SBOM generation – Integration with CycloneDX or SPDX generators allows for compliant Software Bills of Materials.

Compliance & Regulatory Considerations

  • NIST SP 800-161 (Supply Chain Risk Management) requires documented evidence of component provenance. Signed tag creation fulfills this control.
  • ISO 27036-1 (Information Security for Supplier Relationships) mandates verifiable version identifiers. Synthetic internal tags meet this expectation.
  • PCI-DSS and HIPAA environments demand audit-ready reports capturing who created, approved, and deployed each tag.

Score any potential tagging platform against these technical and regulatory imperatives.

Top 3 Solutions / Platforms Reviewed & Compared

1. Internal Fork & Tag Management Platform (e.g., “AOSP-Enterprise Hub”)

Architecture – The hub runs on a dedicated Git server (GitLab EE or Bitbucket Server). It mirrors the upstream AOSP repository nightly and executes a Tag Recreation Engine to generate synthetic tags based on a corporate policy (e.g., enterprise-android-13.0.0-r1).

Key benefits

  • Policy enforcement – Role-based access controls restrict tag creation to signed commits.
  • Auditability – Every operation writes to an immutable audit log in a WORM bucket.
  • ROI impact – IDC’s 2023 “Automation ROI” study shows automating repetitive tagging can reduce engineering effort by 73%, saving a mid-size enterprise roughly $210k annually.

Potential drawbacks

  • Demands on-prem infrastructure and dedicated DevOps resources.
  • Initial setup complexity can delay rollout.

2. Third-Party Continuous Release Service (e.g., “TagSync Cloud”)

Service model – A SaaS that mirrors the public AOSP repository, injects synthetic tags, and notifies CI pipelines via webhooks.

Security posture

  • SOC 2 Type II certified with end-to-end TLS encryption.
  • Supports GPG-signed tags and integrates with Okta for SSO/MFA.

Business case

  • Gartner’s 2024 “Cloud Service Provider Trust” report indicates managed source-code services can reduce total release costs by 12%.
  • Pay-as-you-go pricing suits enterprises with fluctuating build volumes.

Potential drawbacks

  • External dependence introduces third-party risk requiring rigorous vendor assessments.

3. Hybrid Open-Source Toolchain (e.g., “git-rev-proxy + Bazel”)

Design – git-rev-proxy acts as a lightweight HTTP proxy mapping commit hashes to virtual tags on-the-fly. Bazel then references these virtual tags as if they were real Git tags.

Cost profile

  • Licensing – Free.
  • Operational overhead – Requires high in-house expertise to maintain the proxy and harden security.

Security considerations

  • Requires custom signing hooks; the proxy does not enforce GPG signatures by default.
  • The Linux Foundation’s 2023 “Supply Chain Security” report notes that OSS toolchains match commercial security if they adopt policy-as-code.

This approach suits organizations with mature DevSecOps teams capable of absorbing the operational load.

  • Real-time monitoring – Deploy SIEM rules in Splunk or Elastic to alert on tag creation or deletion events that bypass the approved pipeline.

Governance & Policy-as-Code

Embedding governance into the CI/CD workflow achieves continuous compliance without manual overhead.

Lessons Learned & Pitfalls to Avoid

  • Pitfall – Ad-hoc scripts without governance cause drift between source and binary. Mitigation – Use OPA and require peer review for all script changes.
