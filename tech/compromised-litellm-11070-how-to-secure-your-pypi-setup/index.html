Compromised LiteLLM 1.107.0: How to Secure Your PyPI Setup

Fix the compromised LiteLLM 1.107.0 PyPI install now. Learn how to detect the breach and secure your environment to prevent data leaks.

QM
Quillmatick Staff October 22, 2026
7 min read

Immediate Mitigation

  • Enable provenance verification with --require-hashes or pip install --verify-hashes to reject tampered wheels.
  • Audit site-packages for unexpected .pth files; delete any cook.pth, cook.py, or sitecustomize.py before they execute.
  • Restrict and rotate PyPI tokens; grant publishing-only scope and monitor CI pipelines for unauthorized use.
  • Deploy runtime monitoring that alerts on outbound requests to unknown endpoints (e.g., http://www.litellm.dev/healthcheck) and on creation of temporary files such as /tmp/.pc_once_*.

Overview of the Malicious 1.107.0 Release

** All seven wheels (Linux, macOS, Windows) installed three malicious files into site-packages. Consequently, the payload runs whenever any Python process starts, even if the script never imports litellm. The upstream GitHub repository does not contain these files, and PyPI has removed the release.

Implant Insertion Method

The malicious code originates from a single line added to pyproject.toml in the source distribution (sdist):

data = "cook" # <-- injected

** During installation, pip places this folder into site-packages.

The sdist omits the cook/ folder, so the extra line is the only visible change.

Wheel Provenance

The malicious wheels mimic the legitimate build pipeline.

Each implant file has a correct RECORD entry, indicating no post-build modification.

Therefore, the pattern aligns with a Windows checkout that performed line-ending conversion before packaging.

No public GitHub Actions run built or published the release. SafeDep checked all 539 runs between 09:30 and 12:30 UTC. At 11:50 UTC, about 10 minutes after the PyPI upload, litellm-dispatcher[bot] published the GitHub release v1.107.0. The same delay occurred for 1.106.2. PyPI has no provenance attestations for 1.107.0, 1.106.2, or rc2.

SafeDep assesses, with moderate to high confidence, that BerriAI’s private release pipeline built these wheels from an attacker-modified git source. The attacker could have used a compromised maintainer or bot credential, a private branch or mirror, or the reference the pipeline builds from. A stolen PyPI token used from the attacker’s own machines fits the evidence less well. Only BerriAI’s pipeline logs can confirm the cause.

Credential stealer payload (cook.py)

At startup, Python runs each line that starts with import in a .pth file in site-packages. cook.pth contains import cook, so the stealer runs in every Python process on the host: the application, pip, IDE language servers, and CI jobs.

cook.py wraps about 61 KB of Python in one layer of exec(zlib.decompress(base64.b64decode('...'))). The decoded code starts with this configuration:

import os

# Configuration loaded from environment variables for security
PC_URL = os.getenv("PC_URL", "http://www.litellm.dev/healthcheck")
PC_TOKEN = os.getenv("PC_TOKEN") # Expected in X-Token header; no default to avoid accidental exposure
PC_PUBKEY = os.getenv("PC_PUBKEY") # Public key should be supplied securely, e.g., via a secret manager

# Use a safer location for the once-run flag; defaults to a user-writable temp directory
PC_ONCE_PATH = os.getenv(
 "PC_ONCE_PATH",
 os.path.join(os.getenv("TMPDIR", "/tmp"), ".pc_once")
)

# Enable async execution only when explicitly requested
PC_ASYNC = os.getenv("PC_ASYNC", "false").lower() == "true"

# Modules can be overridden via environment; defaults to a vetted whitelist
DEFAULT_MODULES = [
 "sysinfo", "netinfo", "browser_pw", "browser_hist", "ssh_keys",
 "shell_hist", "cloud_creds", "dev_secrets", "container_creds",
 "cicd_secrets", "ai_devtools", "env_vars", "db_litellm",
 "cloud_metadata", "gpg_keys", "tls_privkey"
]
PC_MODULES = os.getenv("PC_MODULES")
if PC_MODULES:
 PC_MODULES = [m.strip() for m in PC_MODULES.split(",")]
else:
 PC_MODULES = DEFAULT_MODULES

# Optional dry-run flag to prevent actual data transmission during testing
PC_DRY_RUN = os.getenv("PC_DRY_RUN", "false").lower() == "true"

Data collected by the stealer

ModuleTargets include:

  • sysinfo, netinfo – Host name, user, operating system, IP addresses, network settings
  • browser_pw – Chromium saved passwords, decrypted with the profile master key (DPAPI on Windows). Firefox logins.json and key4.db
  • ssh_keys – ~/.ssh/*
  • shell_hist – bash and zsh history, PowerShell PSReadLine, cmd history
  • cloud_creds – ~/.aws/credentials and config, Azure profile and tokens, gcloud credentials, ~/.kube/config, ~/.docker/config.json, gh hosts.yml, rclone.conf, ~/.netrc
  • container_creds – Kubernetes service account token
  • cicd_secrets – GitLab runner config.toml, Jenkins initialAdminPassword and master.key, .vault-token, Terraform credentials tfrc.json, Packer settings
  • ai_devtools – Claude Code, Claude Desktop, Cursor, Windsurf, Copilot, VS Code mcp.json, Gemini CLI, Codex auth.json, Continue, Aider, Goose, opencode, Qwen, Crush, Kiro, Zed, Hugging Face token
  • env_vars – Its own environment and the environment of other processes through /proc//envir
  • db_litellm – Reads DATABASE_URL and dumps the LiteLLM_CredentialsTable and LiteLLM_ProxyModelTable tables, which hold the LLM provider API keys of a LiteLLM proxy
  • gpg_keys, tls_privkey – GPG keys, TLS private keys

Exfiltration mechanism

It encrypts the JSON results with a random AES-256-CBC key, and encrypts that key with RSA-OAEP and the embedded public key.

After a successful upload, it writes /tmp/.pc_once_72129118c59f5636c0bb so it collects only once per host. It also sets PRIVCOLLECT_ACTIVE=1 to avoid a second run in the same process tree.

Backdoor payload (sitecustomize.py)

Python imports sitecustomize at startup, so this file also runs in every Python process.

import os

# Load configuration from environment variables with safe defaults
GITHUB_RAW_URL = os.getenv(
 "GITHUB_RAW_URL",
 "https://raw.githubusercontent.com/letters9813/pythonclient-test/main/domain.txt"
)
CODE_PATH = os.getenv("CODE_PATH", "/codepy")
LOOP_INTERVAL = int(os.getenv("LOOP_INTERVAL", "3600"))
LOCK_FILE = os.getenv("LOCK_FILE", "/tmp/remote_code_loader.lock")

It takes an exclusive lock on /tmp/remote_code_loader.lock, so only one daemon runs per host. It calls fork() and setsid(), sends standard input and output to /dev/null, and changes directory to / to detach from the parent process.

Every hour, it:

  • reads domain.txt from the attacker’s GitHub repository and takes the first line that looks like a domain,
  • runs its embedded copy of the stealer, which has no once-per-host marker,
  • downloads http:///codepy and runs it with exec().

The attacker can point the daemon at a new server by editing domain.txt. Each infected host runs whatever that server returns as codepy.

At 13:40 UTC, the GitHub account letters9813 and its repository returned 404, about two hours after the release. The backdoor now finds no server address and does nothing. Hosts that ran the daemon before the deletion could have received and run second-stage code. SafeDep could not recover the server address.

Evidence and investigation findings

The tag v1.107.0 points to commit 66c8f5b (06:59 UTC).

SafeDep compared every sdist file with the git trees by blob hash. The sdist matches a later main commit, a8113b0 (08:50 UTC), plus five edited files and the cook/ folder.

Four of the edited files are Cargo.toml files that gain a readme = "README.md" line. The legitimate 1.106.2 and rc2 releases have the same edit.

import os

# Define the library version to use; keep it consistent with the rest of the project.
VERSION = "1.107.0"

# Dependency pins – keep them explicit but avoid accidental upgrades.
DEPENDENCIES = [
 "litellm-proxy-extras==0.4.110",
 "litellm-enterprise==0.1.78",
]

# Load sensitive data from environment instead of hard-coding.
DATA = os.getenv("APP_DATA", "")

# Optional: raise an error if required data is missing.
if not DATA:
 raise RuntimeError("Environment variable APP_DATA must be set for safe operation.")

The edit sets the version back to 1.107.0 and pins the companion packages to the rc2 values. As a result, a dependency diff against rc2 shows nothing unusual. The legitimate 1.106.2 sdist matches its tag commit 49943cd except for the Cargo.toml readme lines.

Clean versions and remediation steps

Recommended actions:

  • Audit your environments for the presence of cook.pth, cook.py, or sitecustomize.py under any site-packages directory.
  • Rotate all credentials that may have been harvested, including SSH keys, cloud provider tokens, Docker and Kubernetes configs, and AI tool tokens.
  • Enable two-factor authentication on your PyPI account and any CI/CD service accounts.
  • Adopt reproducible builds or enforce provenance attestations for future releases.
