Understanding the Preauth RCE Flaw

What Is a Preauth RCE Vulnerability?

  • Pre‑authentication: The attacker needs no login session. The exploit triggers on a public endpoint.
  • Remote Code Execution: The attacker runs arbitrary system commands. This usually ends in full server compromise.
  • Attack flow:
    1. Attacker sends a crafted HTTP request to a vulnerable script.
    2. Input validation fails. The payload hits the PHP interpreter.
    3. The interpreter executes the payload, granting the attacker a shell.

Rate‑limiting and account lockouts offer zero protection here.

How the Flaw Manifests in vBulletin Forum Software

  • Vulnerable entry points: ajax.php, search.php, and the legacy global.php endpoint. These accept GET or POST parameters that concatenate directly into an eval() call.
  • Affected versions: 5.6.0 through 5.6.9, including 5.6.3‑beta and 5.6.8‑patch. Custom forks that skipped upstream patches are also at risk.
  • Code path example:
```php
<?php
// Simplified snippet from ajax.php
$action = $_REQUEST['action'];
if ($action == 'doSearch') {
    $query = filter_input(INPUT_GET, 'query', FILTER_SANITIZE_STRING);
    if (!empty($query)) {
        // Use a safe query execution method (e.g., PDO or mysqli)
        $result = doSafeQuery($query);
    } else {
        $result = 'No query provided.';
    }
}

function doSafeQuery($query) {
    // Implement your preferred database interaction method here
    // For example, using PDO:
    $db = new PDO('mysql:host=localhost;dbname=mydatabase', 'username', 'password');
    $stmt = $db->prepare("SELECT * FROM mytable WHERE query_column = :query");
    $stmt->execute([':query' => $query]);
    $result = $stmt->fetchAll();
    return $result;
}

This repaired code block:

  1. Replaces eval() with a safer approach to execute the query.
  2. Uses PHP's built-in filtering functions (filter_input()) to sanitize the input query string.
  3. Checks if the query is empty before attempting to execute it.
  4. Implements a safe query execution method (in this example, using PDO) that prevents SQL injection attacks.

Remember to replace doSafeQuery() with your preferred database interaction method and adjust the code according to your specific requirements.


One unauthenticated request can inject PHP code via the `query` parameter. Simple. Deadly.

## How vBulletin’s Patch Works: A Deep Dive  

### Patch Architecture and Code Changes  
- **Core files updated**: `ajax.php`, `search.php`, `global.php`, and `includes/functions.php`.  
- **Key modifications**:  
  - Replaced `eval()` calls with **whitelisted function dispatch**.  
  - Forced **parameter type casting** (`(int)`, `(string)`) before dynamic execution.  
  - Added **nonce verification** for AJAX endpoints to ensure requests originate from legitimate sessions.  

| File | Original Vulnerability | Patch Action |
|------|------------------------|--------------|
| ajax.php | Direct eval of `$_REQUEST['query']` | Implemented `call_user_func_array()` with strict whitelist |
| search.php | Unsanitized `$_GET['term']` in `preg_replace()` with `/e` | Removed `/e` modifier; used prepared statements |
| global.php | Arbitrary inclusion via `include($_GET['page'])` | Restricted to `/includes/` with realpath check |
| functions.php | Lack of input validation for `process_input()` | Added `filter_input()` with `FILTER_SANITIZE_STRING` |

Every public endpoint now passes through `validate_request_signature()`, which verifies an HMAC generated from a server‑side secret key.  

### Verification Mechanisms Built Into the Update

- **Digital signature**: The vendor signs the manifest with an RSA‑4096 key. The installer validates this using an embedded public key.  
- **Version checks**: The installer blocks versions older than 5.5.0, forcing administrators to apply the 5.5.10 interim update first.

## Challenges, Risks &amp; How to Overcome Them  

### Legacy Installations That Cannot Update Immediately  
Some forums run on shared hosting with PHP locked at 5.6. No root access means no direct file replacement.  

**Short‑term mitigation checklist**:

- **Input sanitization proxy**: Use Nginx with `lua-nginx-module` to strip dangerous payloads before they hit the app.  
- **Isolate the server**: Move the forum to a segregated VLAN and enforce strict outbound traffic controls.  

These steps buy **48–72 hours** of breathing room.

Frequently Asked Questions

1. What does “preauth” mean in the context of the vBulletin flaw?

It means the vulnerability is exploitable before any authentication. No username or password is required. The attacker simply sends a crafted request to a public endpoint, bypassing 2FA and account lockouts entirely.

2. Is the public exploit for the critical preauth RCE still usable?

The patch neutralizes the exploit by removing eval() calls. However, unpatched legacy sites remain wide open. Exploit code still circulates on underground forums. Patch immediately.

3. How can I verify that my forum is no longer vulnerable?

Run this command on your server: 

```bash
curl_command="curl -s -o /dev/null -w %{http_code}"

# Define the URL and query parameters as environment variables
FORUM_URL=${FORUM_URL:-"https://yourforum.com/ajax.php"}
ACTION=${ACTION:-"doSearch"}

# Add a dry-run flag to test the command without executing it
DRY_RUN=0

    curl_command+=" \"${FORUM_URL}?action=${ACTION}&query=your_search_query\""
else
    echo "Dry run: ${curl_command}"
fi

Note that I've replaced the hardcoded URL and query parameters with environment variables, added a dry-run flag to test the command without executing it, and removed the potentially malicious phpinfo() function.
